A middleware (middleware.ts, or proxy.ts in Next.js 16) that checks the session runs only for the paths its config.matcher matches. A Clerk middleware written as if (isProtectedRoute(req)) await auth.protect() protects only the paths its createRouteMatcher lists; the issue is then reported on that list. A next-auth middleware whose authorized callback decides by pathname (Auth.js v5's callbacks.authorized with export { auth as middleware }, or withAuth({ callbacks: { authorized } })) protects only the routes for which the callback turns a visitor without a session away (nextUrl.pathname.startsWith('/dashboard'), lists of prefixes with some or includes); a callback the analysis does not follow (a regular expression, a helper call) leaves the matcher alone to decide. Pages and route handlers under dashboard, admin, settings or account that the matcher leaves out, and that check nothing themselves, are open to anyone. The issue is reported on the matcher and lists the routes left out.

A route checks itself with a session call (auth(), getServerSession, currentUser...), a cookie, header or token read, an auth hook (useSession...), a guard component or wrapper, a redirect (also router.replace('/login') in the browser), in the module or a module it imports; a page also through an enclosing layout (or the Pages Router _app) that checks the session and redirects or renders a guard. Public paths (sign-in, sign-up, auth, webhooks, callbacks, public, static, demo) are left out, as are sign-in pages (the signIn page of next-auth's withAuth, a page calling signIn()), placeholder pages that call, await and fetch nothing, route handlers that export no method or only GET under settings (public site settings), and a middleware whose matcher covers no protected-looking route (one meant only for the sign-in page). A Clerk route matcher that lists the public routes (if (!isPublicRoute(req))) protects everything else and is not reported. The matcher follows Next.js semantics: :param, :param*, :param+, :param?, (regex) groups and negative lookaheads such as /((?!api|_next/static).*); an entry with has or missing counts as matching, and a matcher that is not a literal counts as matching everything.

Why is this an issue?

The matcher is a list of paths kept by hand. A section added later (/settings next to /dashboard) is not in it, and nothing else stops a visitor who is not signed in.

Noncompliant code example

// middleware.ts
export { auth as middleware } from '@/auth';
export const config = { matcher: ['/dashboard/:path*'] }; // Noncompliant: app/settings/page.tsx checks nothing

// auth.config.ts, with export { auth as middleware } and a matcher covering everything
callbacks: {
  authorized({ auth, request: { nextUrl } }) {
    if (nextUrl.pathname.startsWith('/dashboard')) return !!auth?.user; // app/settings/page.tsx is let through
    return true;
  },
},

Compliant solution

// middleware.ts
export { auth as middleware } from '@/auth';
export const config = { matcher: ['/dashboard/:path*', '/settings/:path*'] };

// auth.config.ts
callbacks: {
  authorized({ auth, request: { nextUrl } }) {
    const isProtected = ['/dashboard', '/settings'].some((p) => nextUrl.pathname.startsWith(p));
    return isProtected ? !!auth?.user : true;
  },
},
