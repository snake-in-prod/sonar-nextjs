A middleware (middleware.ts, or proxy.ts in Next.js 16) that checks the session runs only for the paths its config.matcher matches. Pages and route handlers under dashboard, admin, settings or account that the matcher leaves out, and that check nothing themselves, are open to anyone. The issue is reported on the matcher and lists the routes left out.

A route checks itself with a session call (auth(), getServerSession, currentUser...), a cookie, header or token read, an auth hook (useSession...), a guard component or wrapper, a redirect, in the module or a module it imports; a page also through an enclosing layout (or the Pages Router _app) that checks the session and redirects or renders a guard. Public paths (sign-in, sign-up, auth, webhooks, callbacks, public, static) are left out, and so is a middleware whose matcher covers no protected-looking route (one meant only for the sign-in page). The matcher follows Next.js semantics: :param, :param*, :param+, :param?, (regex) groups and negative lookaheads such as /((?!api|_next/static).*); an entry with has or missing counts as matching, and a matcher that is not a literal counts as matching everything.

Why is this an issue?

The matcher is a list of paths kept by hand. A section added later (/settings next to /dashboard) is not in it, and nothing else stops a visitor who is not signed in.

Noncompliant code example

// middleware.ts
export { auth as middleware } from '@/auth';
export const config = { matcher: ['/dashboard/:path*'] }; // Noncompliant: app/settings/page.tsx checks nothing

Compliant solution

// middleware.ts
export { auth as middleware } from '@/auth';
export const config = { matcher: ['/dashboard/:path*', '/settings/:path*'] };
